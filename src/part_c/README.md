# Part C — Support Ticket Triage with Guardrails

## Overview

Part C implements an offline support-ticket triage workflow using the supplied simulated language model (`mock_llm.py`). It applies input guardrails and PII redaction before classification, handles transient model failures, validates model outputs, enforces a token budget and routes tickets using customer segment information from Part B.

## Source files

| File | Responsibility |
|---|---|
| `ticket_preprocessing.py` | Loads tickets and applies empty/long-input guardrails |
| `pii_redaction.py` | Detects and redacts email addresses, phone numbers and order IDs |
| `ticket_classification.py` | Builds zero-shot/few-shot prompts, runs classification and records results/retry logs |
| `retry_validation.py` | Exercises transient-error retry handling and records retry attempts |
| `token_budget.py` | Validates structured model output and demonstrates token-budget enforcement |
| `segment_routing.py` | Uses customer segments to route tickets and produces final triage results |

## Input data and guardrails

The supplied ticket dataset contains 164 tickets. Before classification, the pipeline checks for empty ticket text and estimated input length. The configured maximum input length is 400 estimated tokens.

| Skipped empty | 4 |

## PII redaction

The redaction module handles three PII patterns:
- Email addresses
- Phone numbers
- Order IDs

The recorded run applied 278 redactions: 55 email, 91 phone and 132 order-ID redactions. The redaction patterns are applied again to processed text for a residual-PII check. Only redacted ticket text is used as the classification message content.

## Classification

The permitted categories are:
- Billing
- Delivery
- Technical
- Fraud

The pipeline supports:
- **Zero-shot classification:** instructions without labelled examples.
- **Few-shot classification:** instructions with labelled examples.

The prompts request JSON containing `category` and `reason`. Outputs are validated; the pipeline supports controlled keyword fallback and flags invalid/unsupported output for human review.

Recorded classification results:

| Result status | Count |
|---|---:|
| Classified JSON | 135 |
| Classified keyword | 12 |
| Flagged invalid output | 9 |
| Skipped empty | 4 |
| Flagged long | 4 |
| Total | 164 |

A total of 147 tickets were classified in the recorded run.

## Retry handling

Transient model errors are handled with exponential backoff and jitter, with a maximum of three retries. The mock model generated 19 transient errors across the 156 eligible ticket calls in the recorded retry-validation run; the retry mechanism recovered them. Retry records include ticket identifiers, retry numbers and wait durations.

## Segment-aware routing

The final few-shot routing run used a 100,000-token budget and the customer-segment mapping generated by Part B.

| Condition | Destination | Priority |
|---|---|---|
| Empty ticket | Human review | NORMAL |
| Long ticket | Human review | NORMAL |
| Invalid model output | Human review | NORMAL |
| Budget exhausted | Human review | NORMAL |
| Fraud category | Security team | HIGH |
| Premium customer | Premium desk | HIGH |
| Other valid ticket | Support queue | NORMAL |

If no matching customer segment is found, the customer is not treated as Premium. Recorded routing distribution:

| Route | Tickets |
|---|---:|
| Support queue | 102 |
| Security team | 34 |
| Human review | 17 |
| Premium desk | 11 |
| Total | 164 |

All 34 fraud tickets were routed to the security team in the recorded run.

## Verification scope and limitations

The workflow includes checks for input guardrails, residual PII patterns, zero-shot/few-shot prompts, transient retry recovery, output validation, token-budget enforcement and segment-aware routing. The language model is simulated and the datasets are synthetic; the reported accuracy and routing results should not be treated as production performance claims.
